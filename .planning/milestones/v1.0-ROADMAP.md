# Milestone v1.0: MVP

**Status:** ✅ SHIPPED 2026-05-03
**Phases:** 1–3
**Total Plans:** 9

## Overview

django-inspector v1.0 delivers a fully functional, installable Django observability package. It captures requests, SQL queries, and exceptions into a single correlated trace, and presents them through a Telescope-style dashboard served by Django itself. Built for local development use.

## Phases

### Phase 1: Package Foundation & Core Infrastructure

**Goal:** Create an installable Django package with the core tracing system, event storage models, base watcher framework, and middleware — the foundation everything else builds on.
**Depends on:** Nothing (first phase)
**Plans:** 3 plans

Plans:
- [x] 01-PLAN-01: Package scaffolding — pyproject.toml, AppConfig, InspectorSettings, watcher registry
- [x] 01-PLAN-02: Tracing core — contextvars trace_id, InspectorMiddleware
- [x] 01-PLAN-03: BaseWatcher framework, Event model, storage flush, migrations

**Details:**

Requirements: SETUP-01..06, TRACE-01..03, STOR-01

Success Criteria:
1. Developer can `pip install -e .` the package, add `django_inspector` to INSTALLED_APPS, and run `migrate` successfully
2. InspectorMiddleware generates a unique trace_id per request, stored in contextvars, accessible from any code during the request
3. BaseWatcher class exists with enable/disable/record interface; watchers auto-discover on startup
4. Event model stores events with trace_id, event_type, timestamp, and JSON metadata; bulk_create flush works
5. DJANGO_INSPECTOR settings dict controls watcher toggles and INSPECTOR_ENABLED disables all recording

---

### Phase 2: Watchers

**Goal:** Implement the three core watchers (Request, SQL, Exception) that capture real application events and store them with trace correlation. After this phase, every request generates a full trace of what happened.
**Depends on:** Phase 1
**Plans:** 3 plans

Plans:
- [x] 02-PLAN-01: Request Watcher — method, path, headers, body, status, latency, user, IP
- [x] 02-PLAN-02: SQL Watcher — query capture, timing, origin, slow/N+1/duplicate detection
- [x] 02-PLAN-03: Exception Watcher — stack traces, locals, chained exceptions, trace correlation

**Details:**

Requirements: REQ-01..06, SQL-01..07, EXC-01..04

Success Criteria:
1. Request watcher captures method, path, headers, body, status, latency, user, IP for every non-inspector request
2. SQL watcher captures every query with SQL, params, timing, db alias, and origin file/line — inspector's own queries excluded
3. SQL watcher flags slow queries (>100ms default), detects N+1 patterns (3+ similar queries), and detects duplicate identical queries
4. Exception watcher captures type, message, full stack trace with locals, chained exceptions, linked to request trace_id
5. All events from a single request share the same trace_id and can be retrieved together in chronological order

### Phase 3: Dashboard

**Goal:** Build the Telescope-style web dashboard with live feed, per-watcher section pages, detail views with trace timelines, filtering, and HTMX-powered interactions. After this phase, the package is fully usable.
**Depends on:** Phase 2
**Plans:** 3 plans

Plans:
- [x] 03a: Dashboard Foundation — URLs, base templates, self-contained CSS, sidebar, HTMX
- [x] 03b: Management Command — inspector_cleanup with --hours and --dry-run flags
- [x] 03c: Dashboard Pages — views, templates, HTMX interactions, filtering

**Details:**

Requirements: STOR-02, DASH-01..10

Success Criteria:
1. Dashboard served at `/inspector/` (configurable) with navigation between all sections; self-contained CSS with no external dependencies
2. Live feed page shows recent requests with status badges, method, path, latency; auto-refreshes via HTMX polling
3. Request detail page shows full trace timeline: request metadata → SQL queries → exceptions, all in sequence with durations
4. Queries and Exceptions list pages support filtering and show indicators (slow/N+1/duplicate for queries, grouped by type for exceptions)
5. Management command `inspector_cleanup` purges events older than configurable duration; HTMX interactions work without full page reloads

## Milestone Summary

**Key Accomplishments:**
1. Installable Django package with AppConfig, lazy settings layer, and watcher registry
2. UUID trace_id propagated via contextvars (async-safe) across the full request lifecycle
3. Request watcher captures full HTTP metadata including headers, body (truncated), user, session, IP
4. SQL watcher with N+1 detection (3+ similar queries), duplicate detection, slow query flagging, origin file/line tracking
5. Exception watcher with full stack traces, expandable locals, chained exception support
6. Telescope-style dashboard: live feed with HTMX polling, 3-view request detail (timeline/tabs/waterfall), per-section filtering, `inspector_cleanup` management command

**Key Decisions:**

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| Dev-only for v1 | Eliminates sampling/masking/retention complexity. Focus on core value first. | ✓ Correct — zero-friction setup for devs |
| Django templates + HTMX for dashboard | No JS build step, stays in Django ecosystem | ✓ Self-contained CSS, no external dependencies |
| Same DB default | Zero-config setup. Separate DB via Django routing later. | ✓ Works with SQLite, PostgreSQL, MySQL |
| Request + SQL + Exception as v1 watchers | Core debugging trio | ✓ Covers most common debugging scenarios |
| Auto-discover watchers with opt-out config | Minimal setup friction | ✓ Works via AppConfig.ready() |
| Trace-based event correlation | All events tied to trace_id. Foundation for cross-watcher visibility. | ✓ Enables timeline/waterfall views |
| Middleware-driven request watcher | Signal-based not viable — request/response data only in middleware | ✓ Clean integration |
| Django DB instrumentation API for SQL watcher | execute_wrappers preferred over monkey-patching CursorDebugWrapper | ✓ Future-proof |
